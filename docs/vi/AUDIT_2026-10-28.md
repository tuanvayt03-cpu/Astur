## Overlay notification handling — 2026-10-28 follow-up

User-corrected behavior: **do not block/hide/dismiss notifications**. The desired invariant is to let Windows/Zalo/Telegram present and dismiss their toasts normally while Astur does not treat them as independent tiling windows/tabs. The existing Telegram/Zalo main windows must remain managed.

Implementation on `feat/vi-notifications`: a narrow adoption-only predicate in `crates/astur/src/main.rs` recognizes small, captionless, non-resizable `WS_POPUP` windows with `WS_EX_TOPMOST` and without `WS_EX_APPWINDOW`. Only then does `app_window_reject` return `transient-overlay`, before Astur inserts a window in workspace tiling/tab/focus bookkeeping. It never calls `ShowWindow`, `SetWindowPos`, or modifies the notification. Borderless fullscreen apps, titled dialogs, ordinary windows, and explicit app windows are protected by negative regression cases. Preexisting owner/tool/no-activate filtering is unchanged, and no Zalo/Telegram executable is globally excluded.

**Evidence scope**: synthetic Win32 style/rectangle unit tests; fresh Rust Windows CI for `1091d22` https://github.com/tuanvayt03-cpu/Astur/actions/runs/40659722010 PASSED format, catalog, diagnostic syntax, Clippy, tests, and release build. No real Zalo or Telegram popup was visible in the single read-only Win32 snapshot. Therefore this is a tested classifier, **not yet an E2E-confirmed fix for every app-specific popup**. Capture the next occurrence's HWND metadata and compare against classifier before marking C07–C09 PASS.
